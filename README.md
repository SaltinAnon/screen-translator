# 屏幕实时翻译 · ScreenTranslator

Android 原生（Kotlin + Jetpack Compose）的**手机屏幕实时翻译**应用：
抓取屏幕 → ML Kit OCR 定位 → 大模型翻译 → 悬浮窗把译文**原位覆盖**在原文字上。

当前版本：**v1.6.1**

---

## v1.6.1 修了什么

三个都来自用户实测反馈：

1. **「增强 / 全能」档翻完还是原文，屏幕上也显示原文**（用户标注为**主要问题**）→ 根因是**静默失败**：单段推理抛异常时，引擎把空结果 `ifBlank` 成了原文。用户看到「译文 == 原文」只会以为翻译质量差，根本不知道引擎已经坏了。
2. **第三档 870MB 的 NLLB 手机上太慢** → 用户要求「换成单个语言的模型、一对一、不要中转、要快」。**NLLB 整档删除**，第三档改为 **Opus-MT 全覆盖**（同一套单语言对模型，每对约 115MB、亚秒级）。
3. **版本号改为补丁级递增**（+0.0.1）：本次 `1.6.1`，下次 `1.6.2`。

### 问题一：绝不静默把原文当译文（核心修复）

桌面侧用**真实 ONNX + App 自写分词器**逐条验证过 Opus-MT 链路本身完全正常：

| 源句 | 桌面实测结果 | 耗时 |
| --- | --- | --- |
| Hello, how are you today? | 你好,你今天好吗? | 0.16s |
| This is a test. | 这是测试 | 0.05s |
| この漫画はとても面白いです。（经英语接力） | 这本漫画书很有趣 | — |
| 今日はいい天気ですね。（经英语接力） | 今天天气不错,不是吗? | — |

也就是说，**喂法、分词器、模型全都是对的** —— 真机上唯一的差异只可能是 ONNX 调用本身出错（内存不足 / ABI / 模型损坏）。而旧代码在这种情况下：

```kotlin
val translated = try { engine.run(original) } catch (t: Throwable) { "" }   // 吞掉异常
translatedText = translated.ifBlank { original }                            // 空 → 填原文
```

于是失败被**伪装成「翻译成功、只是译文等于原文」**。这正是用户报的现象的根因。

| 层次 | 修法 |
| --- | --- |
| `SubwordTranslator.translateBlocks` | 统计 `failures`；整批跑完**只要有一段失败就抛 `TranslationException`**（全失败 / 部分失败两套文案），由上层显示红色提示条。**不再回退原文** |
| `MlKitOnDeviceTranslator` | 同样的静默回退模式（`catch { text }` + `ifBlank`），一并改为统计 + 抛错 |
| 顺带排查 | `TranslationVerifier` / `TranslationQualityGuard` 确认**只报告不替换**；翻译缓存**不缓存「译 == 原文」**的结果 —— 两处都不是原因 |

### 问题二：第三档 NLLB → Opus-MT 全覆盖

| 对比 | 旧 · NLLB-200 | 新 · Opus-MT 全覆盖 |
| --- | --- | --- |
| 体积 | 约 **870MB**（一次买断） | 约 **115MB / 语言对** |
| 速度 | 手机上单句**数秒** | **亚秒级** |
| 形态 | 一个多语言大模型 | **单语言对**、一对一 |

上游确实没训 `ja→zh`，所以日译中这类方向用**英语快速接力**（两段合计约 0.3 秒），
仍远快于 NLLB 的数秒 —— 这是当前能做到的「最快 + 最好」的取舍。

> `OfflineEngineKind.NLLB` 已删除并替换为 `OPUS_FULL`（id `"opus_full"`）。
> 老用户设置里存的旧 id `"nllb"` 认不出来会**回退到 ML Kit**，重新选一次即可，不会崩。

## v1.6.0 修了什么（历史）

两个都来自用户实测反馈，且都是**真 bug**：

1. **横屏时点翻译球，球变成感叹号、翻不了** → 根因是 `ScreenCaptureManager.resize()` 把 `resize()` 的异常**全部吞掉**，并在重建前先把 `VirtualDisplay.surface` 置空。部分 ROM 上 `resize` 抛一次之后，ImageReader 就再也收不到帧 → `acquireLatestImage()` 恒为 `null` → 手动模式下无法自愈，永远感叹号。
2. **NLLB 又慢又翻不好（不如第二档 Opus-MT）** → 根因是**起始符喂错了**：把「目标语言码」当 `decoder_start` 喂进去。实测会让模型第 0 步 argmax 落在 `▁` 上，然后**无限重复 `▁`**、输出空串、永远碰不到 EOS，128 个 token 预算全烧光。桌面端同一句要 **19~23 秒**且译文为空。

### 问题一：横屏取帧链重建失败（感叹号）

Android 14 起，一个 `MediaProjection` 令牌只能调**一次** `createVirtualDisplay()`，转屏必须用
`VirtualDisplay#resize` + `setSurface` 更新，不能重建。旧代码有两处致命伤：

- `runCatching { display.surface = null }` → 先置空 surface，部分 ROM 会**停止投递帧**；
- 整个流程的异常**被 `runCatching` 静默吞掉**，失败后既不上报也不重试。

| 层次 | 修法 |
| --- | --- |
| 重写 `resize()` | 不再前置置空 surface；异常记录进 `lastResizeError`；`applyResize()` 换上新 surface 后才关旧 reader |
| 取帧验证 | 新增 `verifyFrameLocked()`：resize 后在 600ms 内轮询 `acquireLatestImage`，真取到一帧才算成功 |
| 失败重试 | `resize()` 失败自动**重做一次**；仍失败才记 `lastResizeError` |
| 运行中自愈 | `tick()` 发现 `frame == null` 且 `lastResizeError != null` 时，主动 `resize(force = true)` 一次并重试取帧 |
| 明确报错 | 自愈也失败时，状态栏改为「转屏后取帧链异常，请重新开启翻译」，并弹**红色提示条**告诉用户怎么恢复 |
| 同尺寸早退 | `onCapturedContentResized` 读到尺寸未变时直接 `syncGeometry()` 返回，不做无谓的重建 |

### 问题二：NLLB 的起始符喂错（又慢又烂的根因）

> v1.6.1 已把 NLLB 整档删除，下面是历史记录。`forcedBosId` 这套机制**保留**在
> `OnnxSeq2Seq.Spec` 里（通用能力，将来接别的 seq2seq 模型用得上），只是当前没人用。

HuggingFace 的 NLLB `generate` 流程是：

```
decoder_input_ids[0] = config.decoder_start_token_id   # = 2 (</s>)，不是语言码
forced_bos_token_id  = <目标语言码>                     # 第 0 步强制产出它
```

也就是说语言码是**第 0 步被强制产出的 token**，而不是喂进去的起始符。旧版直接把目标语言码当起始符，实测后果：

```
起始符 = zho_Hans → 第 0 步 argmax 落在 `▁`（15.81，与「的」15.79 几乎并列）
                  → 之后无限重复 `▁`，解码全被 skip 过滤 → 空串
                  → 永远碰不到 EOS → 128 token 全烧光 → 又慢又没结果
```

| 层次 | 修法 |
| --- | --- |
| `OnnxSeq2Seq.Spec` | 新增 `forcedBosId`（HF 的 `forced_bos_token_id`）；`decoderStartId` 对 NLLB 改为 `</s>`(2) |
| 解码循环 | 第 0 步吃起始符、拿到 logits 后**不看 argmax**，直接把 `forcedBosId` 作为第一个生成 token 喂给第 1 步 |
| 顺带修 | `argMaxLast` 必须在 `logits.close()` **之前**调用（否则读的是失效的 buffer） |

**实证结果**（真实 NLLB-600M ONNX，桌面 CPU）：

| 源句 | 修复前 | 修复后 |
| --- | --- | --- |
| Hello, how are you today? | 空串，19.3s | 你好，今天怎么样？ **1.6s** |
| The quick brown fox… | 空串，~23s | 快速的棕狐跳过狗。1.8s |
| Please open the settings menu… | 空串 | 请打开设置菜单，并启用暗模式。2.0s |
| 今日はいい天気ですね。 | 单 token「的」 | 今天是个好天气。1.2s |

> 两档离线引擎的定位（v1.6.1 起）：**ML Kit**（系统自带，最轻，但非英语互译经英语中转）→
> **Opus-MT**（115MB/语言对，亚秒级，常见方向直译；缺的方向英语接力）。
> 「增强 / 全能」两档用的是同一套模型，只是可选方向不同。

## v1.5.1 修了什么

v1.5 的三个问题里有**两个没修干净**，用户装上后立刻又报了出来。这一版是收尾：

1. **横屏时悬浮球依然会消失**（且手动模式下彻底无法翻译）→ 找到真正的死锁：*球的修复逻辑全写在取帧循环里，而手动模式下取帧只在「被点一下」时才跑 —— 球跑到屏幕外就再也点不到，于是永久失联*。改为一条**独立于取帧循环**的守护通路。
2. **两个离线模型都下载到一半报错「不完整」** → 根因是拿**估算的字节数**当校验基准。Opus 编码器真实 `52899742` 字节，而目录里记的估算值是 `52844544`，差约 55KB，于是每个文件下完都被判成坏的。改为以**服务端返回的真实大小**为准 + 本地 manifest + 逐个文件断点续传重试。
3. **Opus-MT 声称支持中日方向，实际连下载都不允许** → 上游确实没有 `ja-zh` 模型，但 `ja-en` 与 `en-zh` 都在。新增**经英语接力**的两段翻译，日译中真的能用了；同时补上被漏掉的 `en → ja`（上游把它命名成 `en-jap`）。

### 问题一：横屏时悬浮球消失（真正的根因）

v1.5 加的那套「按球心比例重排」本身是对的，但它**只在两条路径上被触发**：
`DisplayManager.onDisplayChanged`、以及 `tick()` 里的悬浮球补挂逻辑。而 `tick()` 在**手动模式**下
只在「被点一下」时才执行 —— 球跑到屏幕外之后就再也点不到，形成死锁。

更糟的是部分 ROM 在 App 进入全屏横屏时**根本不发** `onDisplayChanged`，于是两条路径都不通。

| 层次 | 修法 |
| --- | --- |
| 根因 | 起一条**每秒一次**的守护协程（`maintainOverlay`），完全独立于取帧循环：重新读屏幕尺寸 → 无条件把球夹回屏幕内 → 球不在了就补挂 |
| 触发更快 | 覆写 `Service.onConfigurationChanged`（清单里已声明 `orientation\|screenSize`，实测 `configChanges=0x1fa0`）；`onCapturedContentResized` / `onScreenGeometryChanged` 也各调一次 |
| 尺寸读错 | `syncGeometry` 改为**无条件**重新夹一次。以前「尺寸没变就跳过」—— 只要读数有一瞬间还是旧的，球就永远回不来 |
| 尺寸来源 | 优先 `WindowMetrics.bounds`（API 30+，唯一明确按当前旋转给出的值），再用 `Configuration.orientation` 对宽高方向做校正（个别 ROM 旋转瞬间会返回自然方向的尺寸） |
| 用户体验兜底 | 「设置 → 显示 → 悬浮球」新增**「把悬浮球找回来」**按钮，直接让服务把球搬回默认位置并持久化 |

> 顺带修掉一个旧 bug：那个复位按钮只清 `bubbleX/bubbleY`（绝对像素），而 v1.5 起
> `resolveBubblePosition` 优先用 `bubbleXFrac/bubbleYFrac` —— 于是点了等于没点。现在两份一起清。

### 问题二：下载到一半报错「下载出错」

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| 进度走到 ~46%（第一个文件下完）就报「不完整」 | `ModelFile.bytes` 是 `mb(50.4)` 这样的**估算值**，却被当成下载完成的**校验基准**。实测 Opus encoder 真实 `52899742`，估算 `52844544`，永远对不上 | 下载前 `HEAD`（失败则退化为 `GET Range: bytes=0-0` 读 `Content-Range`）问服务端真实大小，**以它为准**校验 |
| 下次启动「是否已下载」判不准 | 只有一个估算值可用 | 下载成功后写 `manifest.json` 记录**每个文件的真实字节数**；`isReady` 优先按它比对，离线也能精确判断 |
| 网络抖动一次就整包失败 | 单次失败即 `return Failed` | 每个文件最多重试 **5 次**，每次用 `Range` 从 `.part` 断点续传；超时放宽到 connect 30s / read 120s |
| 进度显示不实 | 分母用的是估算总和 | 分母改为探测出的真实总字节；接力路线按**全程**给进度，不在第二个模型处跳回 0 |
| 空间检查 | 拿估算值判 | 改为按「还差多少字节」算，且把 `.part` 里已有的部分算进去 |
| 404 被当成可重试 | 重试 5 次纯属白等 | 404 / 401 / 403 直接判死，并给出「仓库可能改名或删档 / 换个源」的说明 |

实测确认（`hf-mirror.com`，2026-10-03）：`HEAD` 返回真实 `Content-Length`；
对 **`onnx/*.onnx`（大文件）**，`Range: bytes=N-` 经 302 到 CDN 后返回
`206 + Content-Range: bytes N-M/52899742`，断点续传在这条链路上是有效的。
（顺带一提：CDN 的签名地址 1 小时过期，续传时重新发请求会拿到新签名，反而更耐用。）
但 **`tokenizer.json` 走的是另一条链路，会忽略 `Range`** —— 见下面「断点续传实测」。

```
Opus en-zh   encoder 52899742 · decoder 60212804 · tokenizer.json  6380952
NLLB 600M    encoder 419120483 · decoder 475505771 · tokenizer.json 17331224
```

#### 断点续传实测（两条链路行为完全不同）

把 Kotlin 的下载循环**逐字复刻**成脚本（`.tmp-verify/verify_download.py`）：先故意只下到一半「断线」，
再从断点续传，最后用 SHA-256 与整包比对。结果 3/3 通过：

| 链路 | 服务端对 `Range: bytes=N-` 的真实反应 | 续传后 SHA-256 |
| --- | --- | --- |
| `opus-mt-en-zh/tokenizer.json` | **回 200 + 完整 body**（完全忽略 Range） | 与整包一致 ✅ |
| `opus-mt-ja-en/tokenizer.json` | 同上 | 与整包一致 ✅ |
| `nllb-200-distilled-600M/tokenizer.json` | 老实回 **206 + 恰好剩余的部分** | 与整包一致 ✅ |

这就是下载器里那条守卫的由来：**只有 `code == 206 && 断点 > 0` 才允许追加写入**。
第二条链路上若按「有 `Content-Range` 就 append」，3.2MB 的断点会接上 6.4MB 的全量 =
9.6MB 的垃圾文件。另外两条链路都必须带 `User-Agent`（`hf-mirror.com` 对无 UA 的请求回 403）。

### 问题三：Opus-MT 的「日译中」

用户的原话是「说好了支持日译中，却不支持日语→中文（简体），甚至不允许下载」——
这句抱怨是对的，而且**两头都有错**：

1. **界面上写着支持**：`OfflineEngineKind.OPUS_MT.detail` 原文是「中日英等常见方向直接对译」，
   用户合理地理解成中日方向可用。**已改写**成明确说明「上游没训过的方向会用英语接力」。
2. **确实没有 `ja-zh` 模型**（`Helsinki-NLP` 没训，`Xenova` 也没转，仓库返回 401），
   但 `ja-en` 和 `en-zh` 都在 —— 所以**接力是可行的**，只是 v1.5 直接把路堵死了。

修法：新增 [ModelRoute] 概念 —— 一条翻译路线可能是**一个**模型包，也可能是**两个**。

```
日语原文 ──[opus-mt-ja-en]──▶ English ──[opus-mt-en-zh]──▶ 中文
```

| 方向 | v1.5 | v1.5.1 |
| --- | --- | --- |
| 英 ↔ 中/法/德/西/俄… | ✅ 直译 | ✅ 直译（不变） |
| 日 → 中 | ❌ 判不支持 | ✅ **英语接力两段** |
| 中 → 日 | ❌ 判不支持 | ✅ **英语接力两段** |
| 韩 → 中 | ❌ 判不支持 | ✅ **英语接力两段** |
| 英 → 日 | ❌ 漏了（上游叫 `en-jap`） | ✅ 直译 |
| 英 → 泰/葡/土/韩 | ❌ | ❌ 仍不支持（上游连英语方向都没训），明确报错并建议换 ML Kit 或云端 |

接力路线由 `OfflineModelCatalog.opusRoute()` 统一决定，**设置页与翻译引擎共用同一个入口**
（`routeFor()`）—— 两边各写一套正是「界面说支持、实际不让下」的根源之一。
设置页会明说「这一方向没有直接模型，要下两个包、速度约为直译的一半」。

## v1.5 修了什么

一次迭代解决三件事，全部来自用户实测反馈：

1. **横屏（如 B 站全屏播放）时悬浮球消失、没法翻译** → 支持横屏，转屏后球的相对位置保持不变。
2. **英译汉有时变成不认识的文字，或翻完还是英语** → 加了译文语言校验 + 质量守门，出问题的译文不再被当成结果，也不再被缓存。
3. **端侧离线模型太普通、效果极差** → 端侧引擎升级为**三档可选**：ML Kit（默认）/ Opus-MT（增强）/ NLLB-200（全能，200 种语言直译）。

### 问题一：横屏时悬浮球消失

两个独立的原因叠在一起：

| 原因 | 说明 | 修法 |
| --- | --- | --- |
| 转屏后服务与渲染状态错乱 | `MainActivity` 与前台服务都没声明 `configChanges`，转屏时 Activity 被销毁重建 | 声明 `configChanges`，服务侧不重建 |
| 球的坐标存的是**绝对像素** | 竖屏时球停在右侧、屏幕高度 42% 处，那个 y 值放进横屏坐标系就跑到屏幕下方去了 | 改存**球心相对屏幕的比例**；旧数据首次升级时反推比例并 clamp 回可见区 |
| 取帧尺寸不跟着变 | 没有 `onCapturedContentResize` 回调 | 监听 `DisplayManager`，转屏后重新协商虚拟显示尺寸 |

`TYPE_APPLICATION_OVERLAY` 窗口**不会**跟着 Activity 旋转缩放，所以这件事只能主动监听、主动重排。

### 问题二：翻完还是英语 / 变成另一种外文

用户描述得很准确：「变成不认识的语言」+「和原文一模一样」。分头查出来是四个原因：

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| 译文和原文**一模一样** | 多模态返回的原文照抄被当成正常结果，还**被写进了 LRU 缓存** —— 于是永久错下去 | 只有 `translatedText != originalText` 才写缓存；再加一道校验，与原文相同即判失败 |
| 变成另一种外文 | 模型返回了非目标语言的文本（例如要求中文却给了日文/韩文） | 新增译文语言校验：比对目标语言与译文实际的文字系统（CJK / 假名 / 谚文 / 西里尔…） |
| 端侧 `auto` 源语言乱翻 | ML Kit 路径对 `auto` **无脑按英语处理** | 按字符构成猜源语言（假名→日、谚文→韩、CJK→中、西里尔→俄…），猜不出才退回英语 |
| 竖排/段落合并后的长句质量差 | 与 v1.3.0 的合并链路有关，见 `LineGrouper` | 保持既有逻辑，由质量守门兜住失败情形并**明确报错**而不是静默回退 |

### 问题三：端侧离线引擎升级为三档

> ⚠️ **v1.6.1 更新**：第三档（NLLB-200）已**整档删除**，换成「**全能 · Opus-MT 全覆盖**」
> （同一套单语言对模型，每对约 115MB、亚秒级）。下面的三档表格是 v1.5 的历史记录。

这是本轮最大的一块。用户的原话是「离线模型太普通导致翻译效果极差」，
而这句话背后是一个**结构性**限制 —— 不是调参能解决的：

```
ML Kit 的端侧翻译模型是「围绕英语」训练的：
    英语 ↔ 其他语言   → 有直接模型
    日语 → 中文        → 没有，只能「日语→英语→中文」中转两次
```

看日本漫画最需要的恰恰是**日译中**。所以 v1.5 给端侧加了两个真正直译的引擎，
做成**用户自选的三档**（`设置 → 模型 → 端侧离线引擎`）：

| 档位 | 体积 | 速度 | 直译（不经英语） | 覆盖 | 适合 |
| --- | --- | --- | --- | --- | --- |
| **标准 · ML Kit**（默认） | 约 30MB / 语言对 | 最快（几十 ms） | ✗ | 59 种 | 英语互译、想零配置 |
| **增强 · Opus-MT** | 约 110MB / 语言对 | 快（亚秒级） | ✓ | 41 个语言对 | 常见方向要质量 |
| **全能 · NLLB-200** | 约 870MB（一次买断） | 慢（数秒） | ✓ | 200 种 | **日译中**、冷门语言 |

实现上是一个完整的端侧推理栈，全部自己写（Android 上没有任何可用的
SentencePiece Java 绑定）：

```
tokenizer.json ─┬─ Unigram（Opus-MT）→ Viterbi 最优切分
                └─ BPE（NLLB）      → 合并优先级 + 紧凑 rank 表
                        ↓
                 ONNX Runtime（encoder + decoder_merged，KV cache 贪心解码）
                        ↓
                 translate/BubbleMerger → overlay 渲染
```

**Opus-MT 的方向缺口要明确拦住**：Xenova 转过 76 个 opus-mt 模型，
与本 App 语言表相关的只有 41 个，缺的恰好是最需要的东亚方向
（`en→ja`、`ja→zh`、`ko→zh`…）。选到这些方向时**不能假装能翻** ——
引擎直接抛错并引导用户换 NLLB 或 ML Kit。

### 离线验证结果（先于真机，全部在本机跑过）

**一、分词器与官方库逐 token 一致。**

自写分词器的最大风险是「能编译、翻出来是垃圾」。所以拿 HuggingFace 官方
`tokenizers` 库的输出当标准答案做了回归（`app/src/test/…/TokenizerGoldenTest.kt`、
`.tmp-verify/jvmharness/`）：

| 模型 | 用例 | 结果 | 加载峰值 / 常驻（多次运行） |
| --- | --- | --- | --- |
| Opus-MT en-zh（Unigram，65001 piece） | 23 | **23/23 一致** | 48~50MB / 9MB |
| NLLB-200（BPE，256204 piece + 51.4 万条 merge） | 23 | **23/23 一致** | 164~181MB / 34MB |

过程中揪出三个**只有对标准答案才会暴露**的坑：

| 坑 | 真相 |
| --- | --- |
| unk 用错了 id | Opus-MT 的 `model.unk_id` **声明是 2**，而 `vocab[2]` 恰好是 `,` —— 按 `<unk>` 的字符串位置去查会得到 1，全错。反过来也绝不能把 2 当控制 token 丢掉，否则译文里的逗号会被吃掉 |
| 未知字符按 char 数算 | `😀` 在 Java 里是代理对（2 个 `char`），按 `char` 迭代会产出**两个** unk；官方只给一个。必须按**码点**迭代 |
| 连续未知没有合并 | `こんに`（3 个字符都不在词表里）官方只产出 1 个 unk，不是 3 个 |
| BPE 的 merge 键 | 一度以为要改成「字符串符号」才能表达 `▁😀`。实测 NLLB 的 **514098 条规则里操作数全部在词表内（0 条例外）**，所以用 id 当键是充分的 —— 这条性质不成立才需要改字符串表 |

**二、端到端：自写分词器的 token → 真实 ONNX 模型 → 可读译文。**

把 Kotlin 分词器编出的 token 导出，直接喂进真实的 ONNX 模型（`.tmp-verify/py_end2end.py`）：

| 原文 | 译文 |
| --- | --- |
| The quick brown fox jumps over the lazy dog. | 棕色狐狸跳过懒狗 |
| I can't believe it's already 2026! | 真不敢相信已经2026年了! |
| This is a test of the offline translation engine. | 这是对离线翻译引擎的测试 |
| Please don't touch that button. | 请别碰那个按钮 |
| Good morning, how are you today? | 早上好,你今天好吗? |

没有重复循环、没有乱码。

**三、顺带揪出一个会整个废掉增强引擎的 bug。**

merged decoder 的喂法有四条硬规则（任缺一条就翻出垃圾）：

1. `present.*` 必须**改名**成 `past_key_values.*` 才能当下一步输入
2. 第 0 步必须 `use_cache_branch=false`，并喂「序列维 = 0」的占位 past
3. **编码器那套 KV 只算一次，之后必须冻结**（缓存分支给出的是 0 长度的退化张量）
4. 源句末尾必须补 `</s>`（漏掉会翻成「快速快速的棕狐狐狐狐狐…」）

而第一版 Kotlin 实现把「冻结的编码器 KV」和「滚动的 decoder KV」混在同一份缓存里，
第 1 步末尾那句「释放上一轮缓存」把**编码器 KV 也一起关掉了**，此后 feeds 里只剩
decoder 那套 → 第 2 步 ORT 直接报
`Required inputs (['past_key_values.0.encoder.key', …]) are missing from input feed`
→ `translate` 被 catch 后返回空数组 → 上层显示原文。

用 `.tmp-verify/py_end2end.py --buggy` 复现了这个行为（每句都在第 2 步失败），
确证它不是读代码读错了。修法是**两类缓存分两个 map**，每一轮 feeds 同时带上。

### 一处工程上的坑（与 App 无关，但会卡住后面的人）

本机工程路径含中文（`C:\Users\闫涵\…`），**Gradle 的 test worker 起不来**：
Gradle 8 会把超长 classpath 写成 `@argfile` 传给 `java.exe`，编码在中文 Windows 上对不上，
java 直接报 `ClassNotFoundException: worker.gradle.process.internal.worker.GradleWorkerMain`
—— 看起来像依赖坏了，其实是路径编码坏了。`testOptions` 里给 worker 加
`-Dfile.encoding=UTF-8 -Dsun.jnu.encoding=UTF-8` 也压不住。

所以额外的验证走了一个**不依赖 Gradle worker** 的通道：直接拿 Gradle 已经编译好的
class 文件，用一个独立 Java 程序加载（`.tmp-verify/jvmharness/`，自带一个
`android.util.Log` 桩）。它验的是**同一份真实字节码**，不是另写一遍。
JUnit 版回归（`TokenizerGoldenTest`）保留在仓库里，在没有中文路径的机器上可直接跑。

一次迭代解决三件事，前两件来自用户实测反馈：

1. **竖排时还是一个泡子好几个框、互相遮挡** → 新增「译文框合并」：翻译完成后把同一个对话泡里的多块译文合成**一个框**。
2. **所有设置挤在一个长页面里，改一项要一路下滑** → 设置页按类别拆成五页，底部导航直接切。

### 问题一：一个对话泡只出现一个翻译框

先看它是怎么来的。原文一句话在同一个对话泡里，但 OCR 是**按行**（竖排时是按**列**）交出来的：

```
一个竖排对话泡（3 列）
  OCR 给 3 个独立的框           → 翻译完就是 3 块译文，横排显示时互相压着
  每列又窄又高，横排译文塞不进
  → widenTallRect 把每列横向撑开 → 撑开后的框直接重叠 → 一泡子糊成一片
```

v1.3.0 的「合并段落换行」本来就是对付这个的，但它用的是**严格的行距判据**：
竖排列与列的间距比正常换行松得多，一旦某两列没被判成同一段，缺陷就复现了。

v1.4.5 加了一道**翻译之后、渲染之前**的收口 —— `BubbleMerger`：

| 环节 | 做法 |
| --- | --- |
| 聚类判据 | 2D 紧邻：**上下叠**（比框高）、**左右并**（比框宽）、**斜着挨着**，任一成立即可 |
| 尺寸相似度 | 方向不同比不同维度 —— 只看框高会误杀竖排（末列通常更短，但字号一样） |
| 长宽上限 | 用**屏幕绝对尺寸**，不用「比成员大 N 倍」（竖排泡宽 = 列数 × 列距，列一多就被误拦） |
| 合并结果 | 包围盒取并集（= 泡子本身）+ 译文按阅读顺序拼接（竖排**从右往左**）+ 居中折行 |
| 作用范围 | 端侧 / 混合 / 多模态**三条路径共用**，所以是「不管怎么翻，一个泡子只有一个框」 |

三档策略：**自动**（默认，只在版面看起来是竖排时才动手）/ **总是合并**（整屏都是对话的场景）/
**关闭**（退回 v1.4.0 行为）。另配一个「合并强度」滑杆，覆盖到 2.75 倍字号的列距。

**连带的修正：「撑宽」挪到合并之后。**

以前是先撑宽再合并。可撑宽会让相邻的列直接重叠，把合并判据赖以工作的「列间距」抹成 0 ——
结果是**不管把合并强度调到哪一档，得到的结果完全一样**（离线推演里一眼看出来的）。
现在改成「先按真实间距合并成泡子，再对剩下的孤零零一列撑宽」，那个滑杆这才真的有用。

### 问题二：设置页拆成五页

原来 13 张卡片挤在一个长页面里，改个悬浮球不透明度要从顶部滑到底。现在按「用户此刻想干什么」分页：

| 页面 | 装什么 |
| --- | --- |
| 首页 | 启动 / 停止、当前状态与耗时统计、权限、教程入口 |
| 翻译 | 怎么触发翻译（点击 / 连续）、三种翻译模式 |
| 识别 | 源 / 目标语言、识别器、文字排版方向、合并段落、OCR 参数 |
| 模型 | 服务商与 API Key、高级参数、离线模型、接口诊断 |
| 显示 | 悬浮球、译文外观、**译文框合并** |

切页会重置滚动位置；页面状态用 `rememberSaveable` 保存，转屏不会跳回第一页。
教程与排障里的「去某张卡片」全部改成了「去某一页」，不再指错地方。

## v1.4.0 修了什么

用户实测反馈两件事：

1. **云端「文字为主」模式**会闪一下「没有返回译文块」的提示，但翻译其实出来了；
   **「整屏多模态」模式**则直接报红色错误、一个字都不翻，错误还一直挂着。
2. **竖排日文漫画**里，同一个对话泡仍被拆成好几段分别翻译，译文块也是竖着排的，不是正常翻译。

### 问题一：多模态拿不到坐标就全盘皆输

先说「有译文却报红错」：缓存命中让译文已经显示在屏幕上，而这一次模型请求失败，
于是 `errors` 非空 → 走「致命错误」分支 → 红色横幅**常驻**。
用户看到的是「译文明明在，却顶着一句翻译失败」。
→ 现在**屏幕上一旦有译文，错误就降级成一次性黄色提醒**（说明这次哪部分没翻出来）；
只有「一个字都没翻出来」才配得上红色常驻。

再说多模态那个真 bug。根因链条在 `TranslationPipeline.processMultimodal()`：

```kotlin
engine.translateFrame(frame, hintBlocks = emptyList(), ...)   // ① 传空 hints

val hints = hintBlocks.takeIf { it.isNotEmpty() }             // ② 于是走「纯多模态」提示词
```

纯多模态提示词要求模型回 `{"blocks":[{"o":…,"t":…,"x":…,"y":…,"w":…,"h":…}]}`，
而解析器遇到没有 `x` 的条目**直接丢弃**。于是：

> 模型（Qwen-VL 系列尤其典型）只肯回译文、不肯回坐标 → 所有条目被丢 → 「没有可用的译文块」
> → 红色错误，整帧一个字都不显示。

而且这条路径**完全跳过 OCR**，手里没有任何可以落地的坐标，想兜底都没料。

**修法**：多模态模式下**先做一次端侧 OCR**（不是为了识别，是为了拿锚点），
一旦首选问法拿不到可解析的块，就**换一种问法重试一次** —— 把 OCR 找到的文字行带编号发过去
（也就是混合模式那套），坐标直接复用 OCR 结果。宁可多花一次请求，也不能让屏幕空着。

顺带把解析器补强：新增不抛错的 `parseOrNull()`，以及
`{"blocks":["第一句\n第二句\n第三句"]}` 这种「整屏译文塞进一个字符串」的形状
（换行拆开后条数正好对得上才采用）。

### 问题二：竖排日文漫画

日本漫画的台词是**竖排、从右往左**的（縦書き），而 ML Kit 的识别器是为**横排**设计的。
它会把每一「列」当成一「行」交出来：

```
竖排原文（3 列，右→左）          直接按横排识别的结果
  こ ん な                    →   「こんな」
  ん な と                        「なこと」
  な と こ                        「こと、」
  と こ 、
```

于是两个毛病一起出现：**语义断裂**（每列被当成独立句子去翻）+
**排版错乱**（每列的框又窄又高，横排译文塞进去只剩一条细线）。

**修法**：识别前把位图**逆时针转 90°**。竖排的「列」就变成横排的「行」，
「右→左的列序」正好变成「上→下的行序」，列内字序也变成左→右 —— 回到 ML Kit 最擅长的排布。

| 环节 | 做法 |
|---|---|
| 判定 | 横排识别的结果里，**三分之二以上**的框「高 ≥ 1.5 倍宽」→ 判定为竖排（横排文本永远不会这样） |
| 重识别 | 转 90° 再识别一次，与横排结果**按得分择优**；自动模式下转过去反而更差就退回横排 |
| 合并 | 关键是**一行代码都没改**：转完之后输入 [LineGrouper] 的已经是横排行，原有判据直接适用 |
| 坐标 | `unrotateCcwRect()` 按 `(x', y') → (W − y', x')` 映射回屏幕 |
| 排版 | 单独一「列」回映射后是又窄又高的框，用 `widenTallRect()` 按框高横向撑开再走折行排版；对齐强制为居中（竖排各列共用顶边，转完会被误判成左对齐） |

误判防护：只对**中文 / 日文**文字系统尝试；阈值取三分之二（宁可漏判让人手动切，也不要误判
把横排内容硬转 90° —— 那样一个字都认不出）。设置里有「自动 / 横排 / 竖排 · 日式」三档手动兜底。

## v1.3.1 修了什么

用户实测反馈：**离线日语翻译时，「日语会经英语中转」这条警告一直挂在屏幕顶部，挡画面。**
希望改成「本次开启翻译后只提示一次」。

### 根因：不是弹太多次，是**它从来就没被收起来过**

两个问题叠在一起：

1. **提示条只负责显示，没有任何自动消失机制** —— 一旦弹出来就永远挂在屏幕最上层，
   直到有别的分支显式调用 `clearBanner()`。
2. **每帧都在「先清掉、再弹出」**：

   ```
   tick() 每帧：
     ① applyHint(preflightHint = null)  →  clearBanner()      ← 清掉，同时把去重状态复位
     ② pipeline 又产生同一个 warning    →  setBanner(warning)  ← 于是去重失效，重新弹出
   ```

   `setBanner` 内部本来有「同一条文本不重复显示」的判断，但第 ① 步把
   `lastBannerText` 置回了 null，所以第 ② 步每帧都能通过检查 —— **等于常驻**。

### 修法

| 改动 | 说明 |
|---|---|
| **提醒只提示一次** | 服务里维护 `shownReminders`，同一句提醒在**本次开启翻译**期间只显示一次；`bootstrap()` 新建会话时清空，`shutdown()` 清干净。配置真的改了（提醒文案变了）会重新提示 |
| **提示条自动淡出** | 非致命提示停留 5 秒后自行收起。红色**致命错误依旧常驻** —— 它是「现在为什么用不了」的说明书 |
| **取消「先清再弹」抖动** | `applyHint()` 不再直接碰提示条，只登记状态。提示条内容统一在帧末按本轮结论决定，去重状态不再被复位 |
| **状态收拢到主线程** | `setBanner`/`clearBanner` 整体切主线程执行，`lastBannerText` 不再被逐帧线程和淡出回调同时读写 |

### 行为对照

| 提示类别 | 例子 | 旧（v1.3.0） | 新（v1.3.1） |
| --- | --- | --- | --- |
| 环境性提醒 | 「日语 → 中文会用英语中转」 | **一直挂在屏幕顶部** | 本次开启翻译只出现 **1 次**，5 秒后自动收起 |
| 即时反馈 | 「没有识别到文字」 | 每帧重新弹出 | 可以再显示，但**最少间隔 25 秒** |
| 致命错误 | 缺权限 / 连接失败 / 语言不支持 | 一直挂着 | 一直挂着（**不变**，它就是「为什么用不了」的说明书） |

> 「本次开启翻译」指的是你点一次「开始屏幕翻译」到停止服务之间。重新开启后提醒会再说明一次 ——
> 这个边界是刻意的：新的会话你未必记得上次说过什么。

顺手修掉一处历史瑕疵：教程与设置页里有几处 markdown 加粗（`**…**`）——
那两个界面是纯 `Text` 渲染、**不解析 markdown**，所以屏幕上会原样显示成星号。已改为普通文字。

## v1.3.0 修了什么

用户实测反馈：**看漫画（对话泡形式）时，一句话被拆成好几行、每行只有几个词，
翻译出来像把一句话当成了很多个短语，语义断裂。**

### 根因：OCR 的最小单位是「行」，但「行」不是翻译单元

```
对话泡原文（一个泡子里的三行）        逐行翻译的结果
  I don't know what                 →  我不知道什么
  you mean by that,                 →  你的意思是这样，
  but I'll try.                     →  但我会试试。
```

每一句单独看都通顺，合起来语无伦次。模型拿到的是「不完整的短语」，只能瞎猜。
这不是模型能力问题，是**喂给模型的输入粒度错了**。

### 修法：先合并成段，再整体翻译

新增 `ocr/LineGrouper.kt`。在 OCR 之后、清洗之前插一步，把属于同一段的行合成一句：

```
对话泡原文  →  "I don't know what you mean by that, but I'll try."
            →  我不明白你的意思，但我会试试。
```

判据分两层：

**硬性条件**（不满足直接不合并）

| 判据 | 说明 |
| --- | --- |
| 垂直紧邻 | 行间距 ≤ 0.7 × 行高。换行文本的行距通常 0.3~0.6 倍行高，而 UI 列表项之间的留白通常 ≥ 0.8 倍 —— 这是区分「同一段被换行」和「相邻两个条目」最有效的一条 |
| 字号接近 | 行高差异 ≤ 40%，挡住「标题 + 正文」被误判成一段 |
| 不是同一行错切 | 上下重叠超过 60% 说明是识别碎片，不是换行 |
| 足够长 | 宽度 ≥ 整帧的 4.5%，且上一行 ≥ 3 个字符。两道一起挡，防止「确定 / 取消」这类两三字按钮标签被凑成一句 |

**打分项**（累计 ≥ 4 分才合并）

| 信号 | 分值 | 为什么有效 |
| --- | --- | --- |
| 来自同一个 ML Kit TextBlock | +3 | ML Kit 本身就是按「段落」聚合的，这是最强信号 |
| 左对齐 / 居中 / 右对齐 | +2 / +2 / +1 | 同一段里的几行必然共享一条对齐边 |
| 字号非常接近（差异 < 18%） | +2 | |
| 上一行是「满行」 | +2 | 说明它是被容器宽度挤下来的，不是一句独立的话 |
| 上一行以逗号/连接号/开引号结尾 | +2 | 明显没说完 |
| 上一行以句末标点结尾 | **−3** | 只减分、**不硬拆** —— 一个对话泡里本来就常有好几句话，硬按句号拆开反而更碎 |

### 拼接细节（直接决定译文质量）

- 中日韩之间**不补空格**（补了会变成「你好 世界」）
- 拉丁文之间补空格
- **中英混排的交界处补空格**（`你好world` → `你好 world`），既好读，也让模型分词更稳
- 英文跨行断词 `thou-` + `sand` → `thousand`（去掉连字符接起来）

### 渲染：合并后的译文要折行，不能压成一行

原来的绘制逻辑是「随框高定字号 + 横向压缩压进扁框」。合并后的框是好几行的并集，又高又宽，
沿用旧逻辑会得到一个巨大字号、再被横向挤成一条细线的结果。

新增 `overlay/InPlaceTextLayout.kt`，两条路径：

| 路径 | 用在哪 | 做法 |
| --- | --- | --- |
| 单行 | 未合并的块（与历史行为**完全一致**） | 随框高定字号 → 按宽度反算缩放 → `textScaleX` 横向挤 |
| 折行 | 合并过的段落 | 固定排版宽度让文字自己折行 → 面积估算起步 → 迭代收敛字号 → 居中/左右对齐按段落原来的对齐边 |

两个实现细节值得记一笔：

1. `StaticLayout` 会**持有**传进去的 `TextPaint` 引用，绘制时才从它复制属性。
   多个 layout 共用同一个 Paint 实例，后面为别的块改字号会连带改掉前面已建好的 layout ——
   所以每个 layout 都克隆一份专属 Paint。
2. 排版在 **composition 阶段算一次**（`remember(blocks, fontSizeScale)`），
   而不是每次重绘都重新测量。StaticLayout 的构造成本不低，放进 `onDraw` 会拖慢整帧。

### 新增开关

「性能与流量」卡片最上方新增 **「合并段落换行」** 开关（默认开）+ **合并强度** 档位
（保守 / 偏保守 / 标准 / 偏激进 / 激进，对应行间距阈值 0.5 / 0.6 / 0.7 / 0.85 / 0.95）。

- 发现「本来分开的两句话被合成一句」→ 调保守
- 发现「同一句话还是被拆着翻」→ 调激进
- 完全不想合并 → 关掉开关，退回 v1.2 的逐行行为

设置页顶部状态栏会显示 `识别 N 行 → 保留 M 段（合并掉 X 行）`，可据此判断有没有生效。
通知栏状态也会带 `· 合并 X 行换行`。

## v1.2.0 修了什么

v1.1.0 实测反馈了两个问题：**离线模式识别/翻译效果极差**、**用阿里云 Qwen 时提示「没有 JSON 中传递的译文块」**。
这一版把两个根因都挖出来修掉了。

### 一、离线模式为什么像乱码 —— 是识别器选错了，不是模型太小

| 问题 | 真实根因 |
| --- | --- |
| 除了英语外其他语言几乎认不出字 | **ML Kit Text Recognition v2 只提供 4 套识别器**：拉丁字母、中文、日文、韩文。旧代码在 AUTO 模式下把所有"不认识"的语言一律丢给**中文识别器**，等于拿汉字识别器去认西里尔文/阿拉伯文/泰文 —— 输出必然是乱码。 |
| 英文识别能力也不强 | 旧代码里 `en` 走的也是中文识别器。中文识别器虽然覆盖拉丁字母，但读英文明显不如专门的拉丁识别器。 |
| 译文大量缺行 | `TextCleaner` 的「已是目标语言就跳过」在目标语言是中文时，把日语行（含 2 个汉字）误判成"已经是中文"直接过滤。日语汉字占比高，于是日译中时大量行根本不进翻译。 |

处理：

- 新增 `ocr/ScriptSupport.kt`：**语言 → 文字系统**的显式映射。拉丁语系（英法德西葡意荷波土越印尼…）→ 拉丁识别器，中日韩各归各的。
- **检测到端侧根本没有该文字系统的识别器时，明确报错**，并且：
  - 云端·文字为主 / 整屏多模态模式下，若服务商有看图模型 → **自动升到「整屏多模态」**（让模型直接看截图），并在屏幕上说明原因；
  - **端侧离线模式下只报错、不偷偷改主意** —— 用户要的是隐私，绝不能擅自把屏幕内容送到云端。
- 源语言选「自动」时，**同时跑拉丁与中文两套识别器，按有效字符数 × 置信度择优**。多花一次 OCR（约 80ms），换英文界面不再被中文识别器拖累。
- `TextCleaner.alreadyInTargetLanguage` 重写：用户**明确声明**了源语言且与目标不同时，完全不做同语言猜测；中文判定必须排除假名/谚文/西里尔文。
- 设置页新增「**当前会用的识别器**」实时提示，选错了一眼就能看出来。

### 二、离线翻译质量差 —— 这是 ML Kit 的固有边界，但以前没告诉你

Google 官方文档写得很清楚：ML Kit 的翻译模型是**围绕英语**训练的，非英语之间会**用英语做中间语言中转**。
所以「日→中」这种语对的质量天生有限 —— 调任何参数都解决不了。

处理：**承认它，并说清楚**。离线卡片里会直接给出警告；某一对需要英语中转时提示改用云端模式；
原来"离线模型没下载好就静默返回原文"（用户只看到译文和原文一模一样、完全不知道为什么）现在改成明确报错 + 给出下一步动作。

### 三、Qwen 报「没有 JSON 中传递的译文块」—— 两个真实原因

| 原因 | 说明 |
| --- | --- |
| **响应解析器太脆** | 旧解析器只认 `{"blocks":[{"i":0,"t":"…"}]}` 这一种形状，只读 `i` 字段。**只要模型没给 `i`（或用了 `index` / 有别的键名），全部 block 都定位不到坐标而被丢弃**，最后抛出「模型返回的 JSON 里没有可用的译文块」—— 模型明明返回了译文。 |
| **百炼的思考模式要求** | 阿里云百炼的 OpenAI 兼容端点对 Qwen3 系列要求：**非流式请求必须显式传 `enable_thinking: false`**，否则报 400（`parameter.enable_thinking must be set to false for non-streaming calls`），或者把正文写进 `reasoning_content` 让 `content` 变成空字符串。旧代码两个都没处理。 |

处理：

- **解析器重写**：多别名索引（`i`/`index`/`idx`/`id`/`n`/`no`/`order`/`position`…）+ **位置回退**（没编号就按数组顺序对应）+ 纯字符串数组 + 按编号做对象 + 嵌套 JSON 字符串 + 直接返回数组，全部支持。真捞不到时，把**模型原始返回的开头**写进错误信息。
- 服务商注册表新增 `extraBodyJson`，**Qwen 默认注入 `{"enable_thinking": false}`**；Gemini 侧用 `thinkingBudget = 0` 达到同样效果；遇到不允许关闭思考的模型会自动去掉该参数重试。
- 新增「**强制 JSON 输出**」开关（带 `response_format`），网关不认该字段返回 400 时**自动去掉重试一次**。
- 新增「**附加请求参数**」输入框：任何接口怪癖都能用一段 JSON 现场解决，不必等新版本。
- `max_tokens` 从 2048 提到 4096；检测到 `finish_reason = length` / `MAX_TOKENS` / `stop_reason = max_tokens` 时给出"输出被截断，请调小单帧行数"的明确提示。
- 连接测试改为**严格判定**：返回正文为空即算失败（旧版本把空回复显示成「连通正常」，正是它误导了排查方向）。
- 新增「**测试看图**」：现场画一张写着 `HELLO` 的图发过去，请模型读出来 —— 真正验证模型能不能看图。
- 新增「**接口诊断**」卡片：保存最近一次请求与模型原始返回（图片数据与 API Key 已脱敏），可一键复制。

### 四、顺手做的改善

- 新增「**OCR 放大倍数**」（默认 1.5×）：小字识别前先放大再识别，中文/日文提升明显；内置约 600 万像素的硬上限防内存爆掉。
- `OCR 输入宽度上限` 默认从 1080 提到 1440。
- 屏幕上/设置里的提示分成**红色（致命）**与**黄色（提醒）**两档：离线品质警告、自动降级原因用黄色条说清楚，不再和真错误混在一起。（v1.3.1 起：黄色条 5 秒自动淡出，同一条提醒每次开启翻译只提示一次；红色仍常驻）
- 教程从 10 节扩到 **12 节**，新增「离线模式到底能干什么（重要）」和「接口诊断：出问题时该提供什么」。

## 三、三种翻译模式

| 模式 | 数据出网 | 需要 API Key | 首次额外成本 | 适合 |
| --- | --- | --- | --- | --- |
| **端侧离线** | 完全不出网 | 不需要 | 下载约 30MB / 语言对 | 隐私敏感、弱网、只想看懂大意 |
| **云端 · 文字为主（推荐）** | 只发清洗后的短文本（可选附一张缩小截图） | 需要 | 无 | 日常主力 |
| **云端 · 整屏多模态** | 发整张屏幕截图 | 需要（且模型必须能看图） | 无 | 排版复杂、OCR 老认错 |

### 混合架构（默认模式）为什么快

1. **端侧**做 OCR，再**把同一段被换行拆开的行合并成一句**，然后清洗 ——
   只留「干净的短文本」：过滤纯数字、纯符号、URL、重复行、已是目标语言的行。
2. **LRU 缓存**（512 条）+ 同帧按原文去重：屏幕内容高度重复，命中率很高，直接省掉一次云端调用。
3. **云端**只回译文，**坐标继续复用端侧 OCR 结果** —— 模型不用猜坐标，覆盖位置天然准确，token 按行计而不是按图计。
4. **不支持看图的模型自动降级**：选 DeepSeek 这类纯文本模型时，App 会自动去掉图片那一步，只发文字，不需要用户做任何切换。

实测口径（1080×2400 屏幕、每帧约 20 行文字）：OCR 约 120~220ms，云端往返约 500~800ms，总感知延迟落在 **0.8~1.2 秒**；纯端侧模式总延迟约 200~350ms。

## 五、使用教程（App 内也有同一份，右上角「使用教程」）

### 1. 30 秒上手

1. 到「权限」卡片把「**显示在其他应用上层**」打开。这是悬浮球能出现在别的 App 上面的前提，不开的话屏幕上什么也看不到。
2. 到「模型服务」选一家服务商、填上 API Key，点「保存并测试」确认连通。不想折腾可以跳过 —— 直接选「端侧离线」模式。
3. 回首页点「开始屏幕翻译」→ 系统弹投屏授权 → 点「立即开始」。

授权后屏幕右侧出现圆形悬浮球。切到任意含外文的 App / 网页，**点一下悬浮球**，译文直接盖在原文上。

> 授权框会提示「共享屏幕内容」，这是 Android 对投屏类 App 的强制要求，没有别的办法绕过。
> 所有画面都只在本机内存里处理，**云端模式除外**（见第 9 节）。

### 2. 悬浮球：唯一需要记住的东西

| 手势 | 行为 |
| --- | --- |
| 单击 | 翻译当前屏幕 |
| 长按 | 快捷菜单：翻译一次 / 清空译文 / 开·关连续翻译 / 打开设置 / 停止服务 |
| 拖动 | 按住拖到别的位置，位置会被记住 |

球的颜色与角标就是状态指示：

- 深蓝 `译` —— 待命
- 蓝色转圈 —— 正在识别翻译
- 绿色 `✓` + 右上角角标 —— 完成，角标是这次翻了多少条
- 红色 `!` —— 出错，屏幕顶部会给出具体原因

### 3. 连续翻译

默认是「点击翻译」。看直播字幕、刷长网页、玩外文游戏时，长按悬浮球 →「开启连续翻译」，或到设置页打开「自动连续翻译」。

- 取帧间隔默认 900ms，调小更跟手但更费电费流量。
- 手动模式下可设置「译文自动消失」（0 = 不消失，双击/长按菜单清空）。

### 4. 模式怎么选

- 只想看懂大意、又怕隐私 → **端侧离线**
- 日常主力 → **云端 · 文字为主**
- 排版复杂、字体花哨、OCR 老认错 → **云端 · 整屏多模态**

### 5. 配置云端模型

1. 打开服务商官网注册并创建 API Key。
2. 在「模型服务」里选中对应服务商 —— 接口地址和常用模型名自动填好。
3. 粘贴 API Key，点「保存并测试」，看到绿色的「连通正常」就成了。
4. 再点一次「**测试看图**」：它会现场发一张写着 `HELLO` 的图，确认这个模型真的能读图。
5. 想换模型直接在「模型名」里手打任意名字。遇到接口有额外要求，用「附加请求参数」填任意 JSON。

服务商的 Key 申请地址见上面的表格（第 4 节）。

> 建议专门为这个 App 申请一个 Key 并在服务商后台设置消费上限。

### 6. 离线模式到底能干什么（重要）

「端侧离线」不联网、不上传、不需要 Key，但它的能力边界比大多数人以为的窄：

**限制一 · 能读哪些文字，取决于 ML Kit 有没有那套识别器，而不是模型大小。**

| | 语言 |
| --- | --- |
| ✅ 能读 | 拉丁字母（英/法/德/西/葡/意/荷/土/越/印尼…）、中文、日文、韩文 |
| ❌ 读不了 | 俄语等西里尔文、阿拉伯语、泰语、希伯来文、希腊语、印地语等印度文字 |

遇到读不了的源语言，**必须改用「云端 · 整屏多模态」**，让云端模型直接看截图。在此之前怎么调参数都只会得到乱码。

**限制二 · 翻译质量只在「英语 ↔ 其他语言」之间才好。**
非英语互译（日→中、韩→中…）会用英语做中间语言中转，质量明显下降。这是 Google 官方文档写明的固有局限。

操作步骤：

1. 到「离线翻译（端侧模式）」卡片选好源语言与目标语言，卡片上会直接告诉你是否支持、质量会怎样。
2. 点「下载 / 检查离线模型」，首次会联网下载约 30MB，保持网络通畅等它跑完。
3. 模式选「端侧离线」，之后即使开飞行模式也能用。

> 离线模型是**一个语言对一个包**。从英译中换到日译中需要再下一个。
> 端侧模式不支持「自动检测语言」，会按英语处理，源内容不是英语请手动指定。

**一句话**：离线模式适合「英文界面翻成中文」。想吃好效果就用「云端 · 文字为主」，
关掉「附带截图」之后它就是纯文字翻译，很快也很便宜。

### 7. 漫画 / 小说：为什么要把整句话一起翻

OCR 的最小单位是「屏幕上的第几行」，但**行不是翻译单元**。漫画对话泡、窄栏小说、
手机上的多行说明，一句话往往横跨三五行，每行只有几个词。逐行翻译时模型看到的是
「不完整的短语」，只能猜 —— 每句单看都通顺，连起来语无伦次。

「性能与流量」卡片最上方的 **「合并段落换行」**（默认开）就是干这个的。
它按**行间距 / 字号 / 对齐边 / ML Kit 自身的段落划分**把同一段的行认出来，先合成一句再整体翻译。

合并完成后，译文会按段落原来的对齐边**折行**排进那个更大的框里，而不是被压成一条细线。

**合并强度怎么调**

| 档位 | 行间距阈值 | 什么时候用 |
| --- | --- | --- |
| 保守 / 偏保守 | 0.5 / 0.6 | 本来分开的两句话被合成了一句 |
| **标准（推荐）** | 0.7 | 默认，绝大多数漫画与正文都合适 |
| 偏激进 / 激进 | 0.85 / 0.95 | 排版很松的漫画，同一句话还是被拆着翻 |

设置页顶部状态栏会显示 `识别 N 行 → 保留 M 段（合并掉 X 行）`，可以据此判断有没有生效。
正常界面（社交 App 列表之类）合并数通常为 0，这也是对的。

> 不想合并（比如你更想逐行对照原文）→ 直接关掉开关，退回 v1.2 的逐行行为。

**收尾：一个对话泡只留一个翻译框（v1.4.5）**

段落合并总有漏网的 —— 竖排列与列之间排得比正常换行松，可能没被合并；而且为了让横排译文
塞得进又窄又高的列框，App 会把这种框横向撑开，撑开之后相邻的框直接重叠。
所以翻译完成之后还有一道收口：把紧挨着的译文框合成一个 —— 包围盒取并集（就是那个对话泡本身），
译文按阅读顺序拼成一段（竖排按**从右往左**的列序），再整体折行排版。
它对端侧 / 混合 / 多模态一视同仁，所以是「不管怎么翻，一个泡子只有一个框」。

位置在「显示」页的 **「译文框合并」** 卡片：

| 档位 | 行为 |
| --- | --- |
| **自动 · 只合并对话泡（推荐）** | 只有版面看起来是竖排（超过一半的框又窄又高）时才动手。普通界面、网页、设置列表保持逐行覆盖 |
| 总是合并相邻文本 | 无条件合并紧邻的译文框。横排漫画、字幕截图最干净；用在设置页 / 网页会把整屏文字糊成一块 |
| 关闭 | 退回 v1.4.0 行为：OCR 给几块就画几块 |

下面的「合并强度」控制「两块之间隔多远还算同一个泡子」，档位覆盖到 2.75 倍字号的列距。
状态栏会显示 `泡子合并掉 N 个框`，可以据此确认有没有生效。

### 8. 调参

| 参数 | 说明 |
| --- | --- |
| **合并段落换行** | 把被换行拆开的句子合成一句再翻译。看漫画、小说、长正文必开（默认开）。详见第 7 节 |
| 合并强度 | 合并的激进程度。合成过头调保守，拆得太碎调激进 |
| **译文框合并（对话泡）** | 翻译完成后把同一泡子里紧挨着的多块译文合成一个框，不再互相遮挡。竖排漫画必开（默认「自动」，只在竖排版面生效）。详见第 7 节 |
| 译文框合并强度 | 两块译文之间隔多远还算同一个泡子。不同泡子被粘成一个框就调保守，同一泡子还是好几块就调激进 |
| 文字系统 | 决定用哪套 OCR 识别器（只有拉丁/中文/日文/韩文四套）。卡片下方实时显示「当前会用的识别器」，选错就是乱码 |
| **文字排版方向** | 横排 / 竖排（日式右→左）/ 自动。默认「自动」会在发现竖排时把画面转 90° 重识别并择优。看日本漫画见第 7 节 |
| **OCR 放大倍数** | 识别前把画面放大几倍。小字（状态栏、列表副标题、游戏 HUD）直接识别容易漏字错字，调到 1.5~2× 提升明显；嫌慢调回 1.0×。默认 1.5× |
| OCR 输入宽度上限 | 放大之前的基准宽度。调大保住细节，调小更快更省电。默认 1440 |
| 单帧最多翻译行数 | 一屏文字多时只翻前 N 行，控成本的主要旋钮；调太大还容易让模型输出被截断 |
| 单次上报字符上限 | 同上，控云端花费 |
| 关闭思考过程 | 思考模型先想再答，慢且容易把 JSON 撑断。默认开启关闭；模型不允许时会自动重试 |
| 强制 JSON 输出 | 带上 `response_format`。网关不认时会自动去掉重试 |
| 附加请求参数 | 填任意 JSON 合并进请求体，用来对付没见过的接口怪癖 |
| 字号缩放 / 底板不透明度 | 译文太小或被压住时调它 |
| 水平·垂直对齐微调 | 译文整体偏移时按 dp 补偿（挖孔屏、曲面屏机型常见） |

### 9. 隐私

- **端侧离线**：画面和文字都在手机内存里处理完即丢，零网络请求。
- **云端模式**：只有**当前这一帧**的数据会发给你自己配置的那家服务商 —— 混合模式发文字，多模态模式发截图。App 本身没有任何服务器。
- **译文缓存**：LRU 约 512 条，进程退出即清空。
- **API Key**：存在应用私有目录的 SharedPreferences，只有本 App 能读。

> 屏幕上如果是银行卡、身份证、聊天记录之类的内容，请用端侧离线模式，或先关掉翻译。
> DRM 保护的视频（Netflix 等）在投屏下是黑屏，这是系统限制，任何录屏/翻译类 App 都绕不过去。

### 10. 常见问题

| 现象 | 处理 |
| --- | --- |
| 看不到悬浮球 | 九成是没给「显示在其他应用上层」权限。去授权后重新点「开始屏幕翻译」 |
| 球在，点了没反应 | 看球是红色 `!` 还是一直转圈。红色看顶部提示条；一直转圈多半是网络不通 |
| 提示条一闪就没了 | 黄色提醒停留 5 秒后自动收起，且同一条每次开启翻译只提示一次（红色致命错误不会消失）。想看完整说明去设置页或教程第 6 / 10 节 |
| 提示「没有识别到文字」 | 确认屏幕上确实有外文；把「OCR 放大倍数」调到 2×；再检查「当前会用的识别器」对不对 |
| 识别出来全是乱码 | 识别器选错，或源语言的文字系统端侧根本没有识别器。看「当前会用的识别器」那行 |
| 竖排日文漫画被拆着翻 | 台词是竖排、从右往左的。把「文字排版方向」手动选成「竖排 · 日式」；生效时状态栏那行的识别器后面会显示「· 竖排」 |
| 竖排翻译后还是好几个框互相遮挡 | 框没被合并。到「显示」页的「译文框合并」确认是「自动」或「总是合并」，再把「合并强度」调大一两档 —— 有些漫画列排得很松，标准档位够不着。看状态栏的「泡子合并掉 N 个框」 |
| 整屏文字被糊成一大块 | 「译文框合并」选到了「总是合并」，会把普通界面的每一行也粘起来。切回「自动」或关掉即可 |
| 多模态模式提示「没有可用的译文块」 | 该模型只肯回译文、不肯回坐标。v1.4 起会自动改用「端侧 OCR 找框 + 让模型填译文」再问一次；仍然失败就换一个带 vision / vl 的模型 |
| 译文一句一句不连贯 | 没把同一段的换行合并起来，被逐行翻译了。确认「合并段落换行」已打开，并把「合并强度」调激进。见第 7 节 |
| 本来分开的两句话被合成一句 | 合并过头了。把「合并强度」往下调一档；个别 App 界面直接关掉「合并段落换行」 |
| 提示「没有可用的译文块」 | 打开设置页最下方的「接口诊断」，把内容复制出来 —— 里面有模型的原始返回 |
| 提示模型正文是空的 | 思考模型没关掉思考过程。确认「关闭思考过程」已打开；若已开启仍报错，多半是该服务商要求流式调用或额度用尽 |
| 译文和原文一模一样 | 离线模式下说明模型一行都没翻动：离线模型没下载好，或该语言对需要英语中转（见第 6 节） |
| 译文位置整体偏移 | 用「水平/垂直对齐微调」补偿，属机型正常差异 |
| HTTP 400 提到 enable_thinking | 该模型的非流式调用必须关闭思考。在「附加请求参数」里填 `{"enable_thinking": false}` |
| HTTP 401 / 403 | API Key 不对，或这个 Key 没有所选模型的权限 |
| HTTP 404 | 接口地址或模型名写错。把服务商切回去一次可恢复默认地址 |
| HTTP 429 | 限流或额度用尽。换服务商，或调小取帧间隔 / 单帧行数 |
| 翻译到一半自己停了 | 多半是系统撤销了投屏或回收了后台服务，重新点「开始屏幕翻译」 |

### 11. 磁贴与通知

- **快捷设置磁贴**：下拉通知栏 → 编辑 → 把「屏幕翻译」拖进面板。磁贴是开关语义（点亮 = 启动，会弹投屏授权；再点 = 停止）。磁贴本身弹不出授权框（系统限制），点它后会闪一个透明页面再弹授权框，这是正常的。
- **常驻通知**：服务运行时通知栏有一条常驻通知，带「翻译一次 / 清空 / 停止」三个按钮。悬浮球被挡住时用它最方便。

### 12. 接口诊断：出问题时该提供什么

设置页最下方有「接口诊断」卡片，保存**最近一次**云端请求与模型的原始返回（图片数据已省略、API Key 已抹掉）。

复现问题后 → 点「查看最近一次交互」→ 整段复制。里面能直接看到请求地址、模型名、HTTP 状态码、完整请求体、
模型返回的原文。界面上只显示一句「失败」的问题，在这里通常一目了然。信息只在内存里，App 退出即清空。

## 七、内存安全设计

| 风险 | 措施 |
| --- | --- |
| ImageReader 缓冲区耗尽 → 后续取帧全 null → OOM | `captureSingleFrame()` 的 `finally` 中**无条件** `image.close()` |
| 每帧新建 Bitmap 造成 GC 抖动 | `BitmapSlot` 复用缓冲，尺寸不变就不重新分配；OCR 用独立 slot |
| 丢帧 / 画面滞后 | `acquireLatestImage()` 自动丢弃队列旧帧 |
| 云端图片过大 | 上传前缩到 ≤ 设定边长（默认 1024px）、JPEG 默认 72 |
| 服务被杀后残留窗口 | `shutdown()` 统一释放：`VirtualDisplay.release()` → `ImageReader.close()` → `unregisterCallback()` → `OverlayRenderer.hide()`（三个窗口全清）→ `stopForeground(REMOVE)` |
| 悬浮球/菜单窗口挡住用户操作 | 一律 `FLAG_NOT_FOCUSABLE`；译文层额外 `FLAG_NOT_TOUCHABLE`，点击全部穿透 |

## 十、已知限制

1. **DRM 内容不可捕获**：Netflix 等受保护视频在 MediaProjection 下是黑屏，系统限制。
2. **Android 14+ 单次授权**：每次启动服务都需要重新确认投屏，无法绕过。
3. **端侧 OCR 只认 4 种文字系统**：拉丁、中文、日文、韩文。俄语（西里尔文）、阿拉伯语、泰语、
   希伯来文、希腊语、印度诸文字**在离线/混合模式下完全不可用**，App 会明确报错并（云端模式下）自动升到整屏多模态。
   这不是模型大小问题，是 ML Kit 就没有对应识别器 —— 换参数解决不了。
4. **端侧引擎各有取舍**（v1.6.1 起**两档**可选，见第 6 节教程）：
   - ML Kit 的翻译模型**以英语为中心**，非英语互译（日→中、韩→中）要用英语中转，质量明显低一档；
   - Opus-MT 直译、质量好一档，但**只提供已收录的 41 个语言对**，缺的恰好是英→日、日→中、韩→中这类东亚方向，
     选到不支持的方向时 App 会明确报错，**不会假装能翻**；
   - 旧版的第三档 NLLB（870MB、单句数秒）已在 v1.6.1 **整档删除**。
5. **离线模型按档位下载**：
   - ML Kit：约 30MB / 语言对，需要 Google Play 服务可用；
   - Opus-MT：约 115MB / 语言对（接力方向约 230MB）。
   模型托管在 HuggingFace，默认走国内镜像 `hf-mirror.com`（官方源在部分网络下不可达），可在设置里换源。
   支持断点续传，中断后重新点一次即可接着下。
6. **纯多模态模式优先用模型给的坐标**：长文本行可能略有偏差。v1.4 起，模型不给坐标时会
   自动退回「端侧 OCR 锚点 + 换问法重试」，此时坐标精度取决于端侧 OCR；想更准可以直接用混合模式。
7. **竖排识别是启发式 + 手动兜底**：判据是「三分之二以上的框高 ≥ 1.5 倍宽」。
   竖排与横排混排在同一屏（比如漫画上方有横排标题）时可能判不出来 —— 手动选「竖排 · 日式」即可。
   反过来，横排内容误选了竖排会一个字都认不出，记得切回「自动」。
   另外竖排会多跑一次 OCR（约几十毫秒），只在确实像竖排时才触发。
8. **思考模型的输出额度**：`max_tokens` 已提到 4096，但若一屏行数很多且模型坚持思考，仍可能被截断。
   App 会明确提示「输出被截断，请调小单帧行数」，而不是给一句无从下手的失败。
9. **横竖屏切换**：靠 `onCapturedContentResize` 重建 Surface 链，切换后第一帧可能不准，第二帧恢复。
10. **悬浮球的可点区域是方形**：视觉是圆形，四个角理论上也能点中，但只有几 dp，实际影响很小。
11. **段落合并靠几何启发式，不是 100% 准确**：判据是行间距 / 字号 / 对齐边 / ML Kit 的段落划分。
    它可能把「两行贴得很紧的相邻 UI 条目」误判成一段，也可能漏掉「排版特别松的漫画」里的续行。
    前者把「合并强度」调保守，后者调激进，都不满意就直接关掉开关。
    两三个字的按钮标签有额外的宽度下限保护，一般不会被凑成一句。
12. **合并后的译文会重排，不再逐行对齐原文**：这是合并的目的（译文才连贯），
    代价是失去「每一行原文对着那一行译文」的对照感。想要对照感就关掉合并段落。
13. **译文框合并是几何启发式，不是 100% 准确**：判据是「框之间够近 + 尺寸同量级」。
    它可能把「紧挨着的两个独立气泡」并成一个框（把「合并强度」调保守），
    也可能漏掉「排得特别松」的同一个泡子（调激进，最高档覆盖到 2.75 倍字号的列距）。
    另外「总是合并」用在普通设置页 / 网页上会把整屏文字糊成一块 —— 那种场景请用「自动」。
    「自动」档本身很保守：只有超过一半的框是「又窄又高」时才判定为竖排版面。
14. **译文框合并后不再逐行对齐原文**：这是合并的目的（译文才连贯、才不遮挡），
    代价是失去「这块译文对应哪一行原文」的对照感。想要对照感就关掉这项，
    或者把档位留在「自动」并只在看竖排漫画时才依赖它。
15. **本版未在真机上做过完整的端到端验证**：编译、签名、清单、资源全部校验通过，
    但悬浮球对齐、各机型状态栏高度、各家模型接口的实际返回需要装到手机上确认。
    出问题时请用「接口诊断」把原始返回贴出来，定位会快很多。
16. **分词器加载峰值**（实测五次，波动来自 GC 时机）：Opus-MT 那一档峰值 48~50MB、常驻 9MB，
    是现在唯一的托管模型档，内存压力小。
    （历史记录：已删除的 NLLB 档峰值曾达 164~181MB，接近低端机堆上限。）
    分词器加载完会常驻，只加载一次。
17. **端侧增强引擎的推理层未在桌面验证**：ONNX Runtime 的 Java 侧是 JNI，
    桌面上起不来，所以 `OnnxSeq2Seq` 的**喂法**由等价的 Python 脚本逐条验证
    （`.tmp-verify/opus_end2end.py`，译文通顺），但 ORT 的 Java 胶水层要装到手机上才见真章。
    **v1.6.1 起这种情况不再静默**：引擎返回空会抛错并显示红色提示条，
    不会再伪装成「译文 == 原文」。请用日志里的 `OnnxSeq2Seq` / `SubwordTranslator` tag 定位。
18. **Opus-MT 不支持「自动检测源语言」**：它是按语言对训练的，选 `auto` 时 App 会明确提醒
    你指定源语言，不会瞎猜。
